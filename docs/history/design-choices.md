# 우리 선택 역사: 디자인과 작업 방식 (2026-11-18 세션)

> 이 사이트의 디자인·작업 방식을 어떤 선택지 중에서 무엇을 왜 골랐는지 시간순으로 남긴다.
> 면접과 포트폴리오 글의 재료다. 상세 근거는 각 장 끝의 결정 기록 링크를 본다.
> 측정하지 않은 것은 "측정 전", 확인하지 못한 것은 "확인 못 함"으로 적는다.

## 요약

- 출발점은 "디자인부터 먼저 고치자"였다. 밝은 파스텔 샘플에서 어두운 바탕 + 셰이더 + 굴절 글래스로 갔다.
- 정적이고 관공서 같다는 피드백으로, 검정 바탕 + 큰 제목 + 디더링 + 모션 중심의 리디자인(D-019)으로 방향을 한 번 더 바꿨다.
- 도구 선택에서 조율자의 첫 제안(Lenis + 직접 구현)이 사용자 질문으로 철회됐고, Lenis + GSAP로 정해졌다.
- 작업 방식은 사용자가 Subagent-driven을 골랐고, 역할을 `.claude/agents/`에 미리 정의했다.
- 현재 D-019는 사용자 승인 대기 중이다. 새 배경·모션·메인 화면은 아직 구현 전이다.

## 0. 시작

- **상황**: 사용자가 "디자인부터 먼저 고치자"고 했다. 당시 상태는 D-011(그레이니 그라데이션 + 리퀴드 글래스 컨셉), D-017 샘플(밝은 종이색 + 파스텔 4색 + 블러 유리 + 좌측 목차), 메인(`/`)은 빈 연결 확인용 페이지였다.
- 관련: [D-011](../decisions/D-011-design-concept.md), [D-017](../decisions/D-017-detail-page-design.md)

## 1. 레퍼런스와 방향

- **상황**: 사용자가 이미지 3장(어두운 그레인 Blur Light 배경, 리퀴드글래스 UI 예시, 해외 그레이니 그라데이션 사이트 모음)을 가져와 "전체적으로 그레이니 그라디언트 디자인에 진짜 찐또배기 글라스모피즘으로 UI, 해외 스타일처럼"이라고 요청했다.
- **읽은 점**
  - 배경은 어두운 바탕 + 번진 빛 + 밝기에 따라 다른 필름 그레인 + 색수차.
  - 글래스의 핵심은 블러가 아니라 **굴절**.
  - 타이포는 자간 넓은 대문자 라벨과 큰 흰 글자.
- **기술적 주의**: SVG 굴절 `backdrop-filter`는 Chromium 계열에서만 동작한다. Safari·Firefox는 블러로 폴백된다.
- **결과**: 다음 장의 바탕 선택으로 이어졌다.

## 2. 바탕 선택

- **선택지**: 1) 어두운 바탕에 빛이 번지는 느낌(조율자 추천), 2) 밝은 파스텔 바탕, 3) 메인은 어둡게·상세는 밝게.
- **누가 골랐나**: 사용자가 **1번**을 골랐다.
- **결과**: D-017의 "밝은 파스텔" 해석이 대체 대상이 됐다(D-011 컨셉 자체는 유지).

## 3. 만드는 방법 (D-018)

- **상황**: 조율자가 배경 A(CSS 그라데이션 유지) vs B(WebGL 셰이더), 글래스 A(블러 + 테두리 빛) vs B(A + SVG 굴절, 점진적 향상)를 제안했다. 사용자가 이미지를 더 보여주며 "이런 느낌을 내려면 WebGL 셰이더가 필요하고 글래스는 SVG 굴절이 필요할 텐데, 뭐가 추천이고 다른 방안이 있나"라고 물었다.
- **조율자 답**: 둘은 경쟁이 아니라 역할이 다르다. 셰이더는 배경, SVG 굴절은 UI 유리다.
- **선택지**
  - 배경 CSS 유지: 밝기 가중 그레인과 색수차는 CSS로 낼 수 없다. 폴백으로 남김.
  - 그레인 이미지를 구워서 사용: 용량이 크고, 움직임이 없고, 코드로 만든 대표작이라는 의미가 약해 버림.
  - 셰이더 + CSS 폴백: 채택.
  - 유리를 WebGL로: DOM 텍스트·접근성과 어긋나고 비용이 커서 버림.
- **누가 골랐나**: 사용자가 "이 안으로 진행하자"고 승인했고, 결정 기록 D-018도 사용자가 승인했다.
- **확정(D-018)**: 셰이더 배경 + SVG 굴절 유리 + CSS 폴백. 순수 WebGL(라이브러리 없음). 성능 장치는 절반 해상도, 30fps, 비가시 시 정지, reduced-motion 정지.
- **작업 순서 합의**: 토큰·CSS 폴백 배경·굴절 글래스 → 셰이더 → 메인 화면.
- 관련: [D-018](../decisions/D-018-dark-grain-shader-and-refraction-glass.md)

## 4. 실행 방식

- **상황**: 계획서를 썼다(Task 4개). 조율자는 Native(직접 구현)를 추천했다.
- **누가 골랐나**: 사용자가 "그래도 Subagent-driven이 코드 검증은 확실할 것"이라며 Subagent-driven을 골랐다. 메인 에이전트는 조율, 서브에이전트는 작업자·검증자·문서 작성자 3역할로 하자고 요청했다.
- **이어진 제안**: 사용자가 "매번 규칙과 역할을 전달하는 것이 토큰 낭비 같으니 미리 세팅하자"고 제안했다. `.claude/agents/`에 portfolio-worker, portfolio-verifier(Edit·Write 도구 없음, 읽기 전용), portfolio-doc-writer(가벼운 모델)를 만들었다.
- **조율자 설명**: 사전 정의의 이점은 토큰보다 읽기 전용 강제, 역할별 모델, 규칙 일관성이다.
- **결과**: 사용자가 다른 프로젝트에도 쓸 공통 방법론 문서를 요청해 [subagent-driven-workflow.md](../methodology/subagent-driven-workflow.md)가 생겼다.
- 관련: [계획서](../superpowers/plans/2026-11-18-dark-glass-foundation.md)

## 5. Task 1~3 실행과 발견

검증자는 작업자의 보고를 믿지 않고 직접 재측정했다.

### Task 1: 어두운 토큰
- 계획의 `--ink-3 #8896a0`이 가장 밝은 빛 위 패널에서 대비 2.96이었다. `#aebac1`로 올렸다. `--ink-2`는 `#b7c3ca`에서 `#cbd5da`로 올렸다. 이유는 WCAG 4.5:1 확보다.
- 검증 통과. 검증자가 발견한 것: 모바일에서 `.glass` 위 작은 글자 대비가 1.96~3.0이다. Task 2의 완료 조건으로 넘겼다.

### Task 2: 어두운 CSS 폴백 배경
- 대비 문제는 가장 밝은 빛(cyan)을 작게 만들어 오른쪽 아래 모서리로 옮겨 UI 뒤를 어둡게 하는 방식으로 풀었다. `.glass`에 어두운 베이스를 까는 방법은 이때 쓰지 않았다.
- 그레인은 흰 입자 + `overlay`. `multiply`는 검은 바탕에서 보이지 않는다.
- 한계: `overlay`라 어두운 영역에서는 그레인이 거의 안 보인다. 밝기 가중은 셰이더 몫이다.
- 검증: 스크롤 7~8단계 × 애니메이션 10시점, 142장 측정. 상세(calm)에서 전 글자 5.36:1 이상.
- 경고: 메인용 vivid는 바탕 위 작은 글자 대비가 2.25~4.36까지 떨어진다. 메인 설계 때 작은 글자는 패널·글래스·어두운 영역 위에 둔다.

### Task 3: SVG 굴절 `.glass`
- `GlassFilters.tsx`(보이지 않는 SVG 필터, `feImage` 가장자리 맵 + `feDisplacementMap`)를 레이아웃에 한 번 렌더한다.
- **막힌 문제**: 계획의 `url() blur()` 순서로 쓰면 필터 영역 밖이 투명해져 블러가 사라지고 뒤 글자가 또렷이 비쳤다. `blur() url()` 순서로 바꿨다(검증자가 재현).
- 블러를 24→20px로 낮춰 대비를 확보했지만 굴절이 눈에 거의 안 보였다(켜기/끄기 픽셀 차이 평균 0.4~0.7/255).
- 정보 패널 뒤가 매끈한 어두운 빛이라 구조가 없어 굴절이 안 보이는 한계도 확인했다. **굴절은 유리 뒤에 큰 글자·선·빛의 경계 같은 구조가 있어야 보인다.**

## 6. 사용자 피드백과 방향 전환 (D-019)

- **상황**: 사용자가 지금 디자인이 "너무 정적이고 해외 디자인 스타일 같지 않다", "가독성은 좋은데 너무 시원시원하지 않아, 한국 관공서 느낌"이라고 했다. 레이아웃을 시원하게, 스무스 스크롤과 예쁜 애니메이션을 요청했다.
- **새 레퍼런스 3장**
  - #6: 디더링 도트 그라데이션 + 검은 카드 + 픽셀 숫자.
  - #7: 흰 바탕 흐린 덩어리 위에 `[1,0]` 문자와 도트 조각이 움직임. 문자로 만든 나비 같은 디지털 느낌.
  - #8: 검정 바탕 위 주황·파랑·빨강 곡선, 색 점 그레인, 중앙의 거대한 제목, 글래스 알약 네비.
- **누가 골랐나**: 사용자가 우선순위를 정했다. **#6, #8이 가장 우선, #7 같은 디지털 느낌은 살려도 괜찮은 후순위.**
- **조율자 진단**: 좌측 목차·박스 중첩·균일 여백·작은 제목의 문서형 구조, 움직임이 배경 하나뿐, 청록 단색 팔레트, Noto Sans KR 인상.
- **제안한 방향(D-019)**: 검정 바탕 + 주황·파랑·마젠타 곡선, 셰이더에서 베이어 디더링(#6)과 색 점 그레인(#8), 풀폭 섹션과 거대 제목, 상세 페이지의 목차·박스 제거, 모션 추가.
- **결과**: D-018의 팔레트·작업 순서가 D-019로 대체됐다. 어두운 바탕·셰이더·굴절 글래스(C 값)는 유지한다.
- 관련: [D-019](../decisions/D-019-redesign-bold-editorial.md)

## 7. 모션 라이브러리 논의

- **상황**: 조율자가 처음에 Lenis(스크롤) + 직접 구현(CSS·IntersectionObserver)을 제안했다. 의존성을 줄이려는 의도였다.
- **사용자 질문 1**: "GSAP를 쓰면 되지 않나, Lenis를 쓰려는 이유는?" 조율자가 입장을 철회했다. Lenis는 스무스 스크롤, GSAP는 애니메이션 엔진으로 역할이 다르다. 요청한 효과(줄 단위 마스크 등장, 스크롤 연동, 카운트업)는 GSAP가 가장 잘하고, 직접 구현하면 코드가 늘고 완성도가 떨어진다.
- **사용자 질문 2**: "Motion 플러그인과 GSAP의 장단점을 따져보자. Motion이 낫다면 Lenis 없이 GSAP만으로도 되지 않나."
- **비교**
  - Motion: React 선언형, 제스처·스프링·레이아웃/exit 애니메이션에 강하다. 스크롤 연출(pin·scrub)과 글자 분할이 약하고 스무스 스크롤 기능이 없다(Motion을 고르면 Lenis가 필수).
  - GSAP: ScrollTrigger·SplitText·타임라인이 강하다. React와 결이 달라 `useGSAP` 정리가 필요하고 번들이 크다.
  - 스무스 스크롤: GSAP ScrollSmoother(래퍼 transform 방식이라 sticky·앵커·Next 페이지 전환 충돌 우려) vs Lenis(네이티브 스크롤 유지).
- **선택지**: A) GSAP만(ScrollSmoother 포함), B) Lenis + GSAP, D) Lenis + Motion. 조율자 추천은 B.
- **누가 골랐나**: 사용자가 "B로 가자 Lenis + GSAP"로 골랐다.
- **이유**: 이 프로젝트는 스크롤 연출이 핵심이라 GSAP가 맞다. Motion은 관리자 정렬 UI(D-006) 때 재검토할 여지가 있다.
- **라이선스**: 웹 검색으로 확인했다. npm `gsap` 패키지의 플러그인(SplitText, ScrollSmoother 포함)이 상업적 사용까지 무료다(Webflow가 표준 라이선스로 공개). 약관은 바뀔 수 있어 도입 시점에 전문을 확인한다.
- **발견**: Lenis는 GSAP 티커 연결 공식 패턴(`lenis.raf`, `ScrollTrigger.update`, `lagSmoothing(0)`)이 있다. 다만 Lenis + GSAP + WebGL의 모바일 성능 이슈 보고가 있어 모바일 측정이 필요하다(측정 전).
- **되돌아볼 점**: 조율자의 첫 제안은 사용자의 질문 두 번으로 바뀌었다. 도구는 "의존성이 적은가"보다 "요청한 효과를 누가 가장 잘 하는가"로 골랐다.
- 관련: [D-019](../decisions/D-019-redesign-bold-editorial.md)

## 8. 현재 상태

- D-019(`docs/decisions/D-019-redesign-bold-editorial.md`)는 작성됐고 README·D-018 상태가 갱신됐다. **사용자 승인 대기 중**이다.
- 승인 후 새 계획서(셰이더 배경 → 모션 기반 → 메인 첫 화면 → 상세 리디자인 → 문서·검증)를 쓰고 작업자·검증자·문서 작성자 흐름으로 진행한다.
- 기존 인수인계 규칙: 사용자는 답을 바로 받기보다 함께 탐구하는 방식을 선호한다. 커밋은 요청할 때만 한다.

## 9. 방식에서 얻은 교훈

- 검증자가 찾은 문제는 "이번 Task에서 고칠지 / 다음 Task로 넘길지"를 명시해 넘긴다.
- 작업자가 측정하지 않은 항목은 검증자에게 지정한다.
- 검증자는 작업자의 측정 스크립트도 믿지 않고 로직을 읽는다.
- 검증 환경에서 못 하는 것(Safari·Firefox)은 "확인 못 함"으로 사용자에게 넘긴다.
