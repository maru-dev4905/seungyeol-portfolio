# D-008 페이지별 렌더링 방식

- 상태: 확정
- 날짜: 2026-11-17

> 방문자 페이지는 전부 미리 만들어두고(SSG·ISR), 관리자만 브라우저에서 그린다(CSR).

## 결정

| 페이지 | 방식 | 이유 |
| --- | --- | --- |
| 메인 `/` | SSG + 인터랙션 부분만 클라이언트 컴포넌트 | 서버 데이터가 없고 검색에 나와야 한다 |
| 소개 `/about` | SSG | 메인과 같다 |
| 목록 `/projects` | ISR (온디맨드 재검증) | 데이터는 있지만 관리자에서 저장할 때만 바뀐다 |
| 상세 `/projects/[slug]` | ISR (온디맨드 재검증) | 자주 안 바뀌고, 바뀌는 시점을 내가 안다 |
| 관리자 `/admin/*` | CSR + TanStack Query, 로그인 확인만 서버 | 검색에 나오면 안 되고, 화면에서 데이터를 계속 바꾼다. 미리 만들어 저장하면 옛 데이터가 보일 수 있다 |

**판단 기준(페이지마다 묻기):** 데이터가 있나? 언제 바뀌나? 검색에 나와야 하나? 브라우저에서 데이터를 바꾸나?

## 틀렸다가 바로잡은 것

- 서버 데이터가 없는 페이지는 CSR이 아니라 **SSG**다. CSR은 빈 HTML을 받아 브라우저가 다 그려서 첫 화면이 늦고 검색에 불리하다.
- `'use client'`는 CSR이 아니다. 클라이언트 컴포넌트도 서버에서 HTML로 먼저 만들어지고 브라우저에서 하이드레이션된다.
- 하이드레이션은 SSR만의 특징이 아니라, 클라이언트 컴포넌트가 있으면 어느 방식에서나 일어난다.
- 리스트는 "서버 데이터가 있다"만으로 SSR이 되지 않는다. SSR은 **요청마다** 새로 만든다.

## 온디맨드 재검증

관리자에서 저장하는 순간 `revalidatePath` 또는 `revalidateTag`로 해당 페이지만 새로 만든다.
60초마다 확인하는 방식(백석 전시)보다 빠르고 낭비가 없다. 안전망으로 시간 기반 revalidate(예: 1시간)도 걸어둔다.

## 저장 → 재검증 흐름 (B안)

```
브라우저 ──Server Action──▶ Next 서버 ──저장──▶ Nest (DB)
                            Next 서버 ◀──성공── Nest
                            Next 서버: revalidatePath / revalidateTag
```

| 안 | 방식 | 결과 |
| --- | --- | --- |
| A | 저장 성공 후 브라우저가 따로 재검증 요청 | 브라우저의 두 번째 네트워크 요청이 실패할 수 있고, 막으려면 재시도 코드를 따로 짜야 함 |
| **B** | Server Action 하나가 Nest 저장을 요청하고, 성공하면 같은 자리에서 `revalidatePath` | **채택**. 실패 지점이 구조적으로 없음 |

- 로그인 토큰은 httpOnly 쿠키로 서버에만 둔다.
- TanStack Query는 `useMutation`의 `mutationFn`에 Server Action을 넣어 그대로 쓴다.
- 재검증 Server Action도 로그인 확인을 한다.

## 관리자 보안

CSR로 만든다고 검색에서 빠지는 것은 아니다.
- `robots: { index: false }` 메타데이터
- 미로그인 시 `/admin/login`으로 리다이렉트 (미들웨어)
- **진짜 권한 검사는 Nest API에서**

## 면접 포인트

- SSG / ISR / SSR / CSR을 페이지 성격(데이터 유무, 변경 시점, 검색 노출)으로 골랐다.
- "저장 후 재검증을 왜 Server Action 안에서 했나?" → 두 번째 요청 실패 지점을 구조적으로 없애려고.

## 후속: Cache Components 반영 (D-015)

세팅 중 Next 16.4 템플릿이 `cacheComponents: true`를 기본으로 켜둔 것을 발견했고(D-015), 켠 채로 가기로 했다.
이 문서의 **판단(어떤 페이지를 정적/ISR/CSR로 할지)은 그대로**이고, 구현 표현만 바뀐다.

| 이 문서의 표현 | Cache Components 모델에서 |
| --- | --- |
| ISR (온디맨드 재검증) | `use cache` + `cacheTag`로 데이터를 캐시하고, 정적 셸을 즉시 제공 |
| `revalidatePath` / `revalidateTag` | 저장 직후 확인이 필요하므로 Server Action에서 `updateTag` (지연이 괜찮으면 `revalidateTag(tag, 'max')`) |
| 시간 기반 revalidate (안전망 1시간) | `cacheLife` |
